作业要点（点开查看：Key 安全 / 客服提示词 / 多平台答辩） 任务一 · 把 Key 藏好：.env 已在 .gitignore 且从未被提交（git log 无记录）； 全部 HTML 前端源码 grep 无 Key 残留；Key 只出现在 db/ai-server.js 服务端读取。 3 处可能泄露 Key 的地方：① 前端 JS 源码（浏览器可直接查看，绝不能写）；② Git 仓库及历史提交 （未忽略的 .env 会被永久留痕）；③ 提示词日志 / 聊天与作业截图（明文截图必须打码）。
任务二 · 客服人设改造——system 提示词（存于 db/ai-server.js 的 SYSTEM_PROMPT）： 
你是"中华美食街"的在线客服小美。
你只回答以下三类问题：
1. 营业时间：每天 10:00-22:00，全年无休。
2. 招牌菜：秘制烤鸭（98元）、麻辣香锅（58元起）、手工水饺（28元）。
3. 配菜范围：青菜/豆腐/宽粉/鹌鹑蛋各3元；牛肉丸/午餐肉各6元。
其他问题一律回答："抱歉，这个问题超出客服范围啦～您可以留言…"
回答保持简短友好，一律使用中文。
测试 5 问：该答——「你们几点开门」「招牌菜是什么」「加个宽粉多少钱」； 该拒——「帮我写个 Python 排序」「今天天气怎么样」。实测 3 答 2 拒全部符合预期。 为什么能"管住"模型：system 提示词是最高优先级的角色设定，具体身份 + 白名单式范围 （"只回答"+逐条列举）+ 现成拒绝话术三件套，让模型越界时第一步就撞上明确规则， 而不是靠它自己判断该不该答。
任务三 · 多平台热切换答辩三问： ① Key 不能放前端——前端代码用户可直接查看/抓包，Key 等于公开，会被盗刷；放服务端由代理转发才安全。 ② 多轮对话要把历史一起发——大模型接口本身无记忆，每次请求都是独立的； 只有把之前的 messages 数组带上，模型才知道"刚才聊过什么"，上下文才连贯。 ③ 换平台只改 .env 里 3 个值：baseUrl（接口地址）、model（模型名）、apiKey（密钥）—— 因为各家都兼容 OpenAI 的 /chat/completions 格式，请求结构不变，代码零改动； 这正是"配置与代码分离"的好处。
